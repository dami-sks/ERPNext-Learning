Section 01

01Foundation

Two days. The goal is reading literacy, not writing ability. By the end of this section, you will be able to pick up any Frappe Server Script, read it line by line, and explain what it does to a client in plain English. You are not learning to write Python. You are learning to review it.

DAY 01
Python Reading Literacy

Objective: Read a Frappe Server Script without confusion. Understand what every line is doing even if you could not write it from scratch.

Variables and Data Types

A variable is a named container. It holds a value. In Frappe, nearly everything you interact with is stored in a variable first.

customer_name = "Acme Ltd"     # string — text in quotes
total = 1500.00                # float — decimal number
count = 5                      # integer — whole number
is_active = True               # boolean — True or False
Dictionaries

The most important concept for Frappe work. A dictionary holds key-value pairs, like a form with labelled fields. Every Frappe document is a dictionary under the hood. When Claude writes doc.customer_name, it is accessing a dictionary key called customer_name on the document object.

invoice = {
    "customer": "Acme Ltd",
    "total": 1500,
    "status": "Draft",
    "items": []          # empty list — more on this below
}

# Two ways to access a value
invoice["customer"]       # returns "Acme Ltd"
invoice.get("customer")   # safer version — returns None if key is missing
Lists and For Loops

A list is an ordered collection of items. A for loop runs a block of code once for each item in the list. Every child table in ERPNext (like the Items table on a Sales Invoice) is a list. Every automation that touches line items uses a loop.

items = ["pen", "notebook", "stapler"]

# Loop through each item
for item in items:
    print(item)   # runs once per item in the list

# In Frappe: looping through a Sales Invoice's items child table
for row in doc.items:
    print(row.item_name, row.qty, row.rate)
Functions

A named block of code that runs when called. Functions take inputs (parameters) and return outputs. You will read many functions in Server Scripts. You need to know where a function starts, where it ends, and what it returns.

def calculate_total(qty, rate):
    # This runs when the function is called
    return qty * rate

# Calling the function
result = calculate_total(5, 300)   # result = 1500

# In Frappe, functions are methods on a document class
def validate(self):
    # self is the document. self.total is doc.total.
    if self.total < 0:
        frappe.throw("Total cannot be negative")
If / Else Logic

Frappe validation logic is almost entirely built from if/else blocks. Read them as plain English: if this condition is true, do this. Otherwise, do that.

# Basic if/else
if doc.status == "Submitted":
    frappe.throw("Cannot edit a submitted document")
else:
    doc.save()

# elif for multiple conditions
if doc.total > 100000:
    doc.approval_required = 1
elif doc.total > 50000:
    doc.approval_required = 0
    doc.flag_for_review = 1
else:
    doc.approval_required = 0
How to Learn This

Do not use a video course. Open replit.com, create a new Python repl, and type each concept by hand. One hour of typing beats three hours of watching. The goal is not memorisation. The goal is recognition: when you see a loop or a dictionary in a Server Script, you know immediately what it is doing.

End of Day Exercise

Ask Claude to give you three real Frappe Server Scripts at increasing complexity. For each one, write one paragraph in plain English describing what it does. No technical jargon. Write it as if you are explaining the business logic to a client. Do not move to Day 2 until you can do this without hesitation.

DAY 02
Frappe's Specific Vocabulary

Objective: Recognize Frappe's core API calls on sight. Understand the Client Script structure. Learn to read a bench error log. Frappe has maybe six API calls that appear in 80% of all scripts. Today is learning to recognize them.

How a DocType Maps to Python

When you call frappe.get_doc(), Frappe fetches a document from the database and returns it as a Python object. Every field on the DocType becomes an attribute. You already know what these fields are from your implementation work. Now you know how to access them in code.

doc = frappe.get_doc("Sales Invoice", "SINV-0001")

# Every field on the DocType is now an attribute
doc.customer          # the customer field value
doc.posting_date      # the date field value
doc.grand_total       # the total field value
doc.status            # "Draft", "Submitted", etc.

# Child tables (like line items) are lists
for item in doc.items:
    print(item.item_name, item.qty, item.rate)
The Six Core API Calls

Learn these by recognition, not memorisation. Claude will write the code. You will read it and verify the logic makes sense against the DocType you know.

frappe.get_doc("DocType", "Name")
Fetches a single complete document from the database. Use when you need the full record including all child tables. Returns a document object with all fields as attributes.
frappe.get_all("DocType", filters={}, fields=[])
Fetches a list of documents matching the filter conditions. Returns a list of dictionaries. Use when you need multiple records — for example, all submitted invoices for a customer.
frappe.db.get_value("DocType", "Name", "fieldname")
Fetches a single field value from a single document. Lighter than get_doc when you only need one value. For example, getting a customer's payment terms without loading the full Customer document.
frappe.db.set_value("DocType", "Name", "fieldname", value)
Updates a single field value directly in the database. Bypasses the document save cycle. Use in on_submit hooks to update related records without triggering their own validation.
frappe.throw("Your error message here")
Stops execution immediately and shows a red error message to the user in the browser. This is the only correct way to communicate validation failures in Frappe. Never use raise or print for user-facing errors.
frappe.new_doc("DocType")
Creates a new document object in memory without saving it. Set fields on it, then call .insert() to save to the database. Use in on_submit hooks to auto-create related records.
Client Script Structure

You already understand JavaScript from website work. The Frappe Client Script pattern is just a wrapper Frappe adds around standard JS. The structure is consistent: a DocType name, then event handlers as an object.

frappe.ui.form.on("Court Booking", {

    // Runs every time the form loads or refreshes
    refresh: function(frm) {
        // frm is the form object. frm.doc is the document.
        console.log(frm.doc.member_name);
    },

    // Runs when the coach field changes
    coach: function(frm) {
        // Fetch hourly_rate from the linked Coach Profile
        frm.set_value("hourly_rate", frm.doc.coach_hourly_rate);
    },

    // Runs when start_time changes
    start_time: function(frm) {
        // Recalculate total price
        calculate_price(frm);
    }
});
Reading Bench Error Logs

When a Server Script breaks, the error appears in two places: a red error message in the browser (which Frappe shows via frappe.throw), and the full Python traceback in the bench terminal. The terminal traceback is the diagnostic tool.

A Python traceback reads bottom to top. The last line is the actual error. The lines above show you the call path that led to it. Find the last line first. That tells you what broke. Then read upward to find which line of your code triggered it.

# Example traceback — read from the bottom
Traceback (most recent call last):
  File "/apps/frappe/frappe/model/document.py", line 1012, in run_method
    return frappe.call(fn, *args, **kwargs)
  File "/apps/kuwa_tennis/kuwa_tennis/doctype/court_booking/court_booking.py", line 23, in validate
    self.check_booking_conflicts()
  File "/apps/kuwa_tennis/kuwa_tennis/doctype/court_booking/court_booking.py", line 31, in check_booking_conflicts
    existing = frappe.get_all("Court Booking", filters={"court": self.court})
AttributeError: 'NoneType' object has no attribute 'lower'
# ↑ This is the actual error. self.court is None. The court field was empty.

DAY 03
Custom DocTypes with Intent

You have built DocTypes before during implementations. This day is different. You are building with a developer mindset, not a configuration mindset. Every field name you create becomes a Python variable name.

Field Naming Discipline

Use snake_case throughout. customer_name not "Customer Name". No spaces. This is not stylistic preference. It is functional: doc.customer_name works. doc.Customer Name is a syntax error. Your field names become Python variable names the moment you write a Server Script.

Field Type Reference
Field TypeUse ForCode Access
DataShort text — names, codes, identifiers. Max ~140 chars.doc.customer_name
Text EditorLong text — notes, descriptions, rich text.doc.notes
LinkRelationship to another DocType. Creates a foreign key. Always specify the linked DocType.doc.court (returns the linked doc name)
CurrencyMoney. Always use Currency, never Float, for financial values. Respects precision settings.doc.total_price
IntWhole numbers — quantities, counts, stock levels.doc.stock_quantity
FloatDecimals — hours, percentages, rates where sub-unit precision matters.doc.duration_hours
DateDate only. No time component.doc.booking_date
TimeTime only. No date component.doc.start_time
CheckBoolean true/false flag. Renders as a checkbox.doc.is_active (returns 0 or 1)
SelectFixed dropdown options. Options defined in the field settings.doc.surface_type (returns the selected option string)
TableLinks a Child Table DocType for repeating line items.doc.items (returns a list of child rows)
Child Tables

A Child Table is its own DocType with "Is Child Table" checked. It has three auto-managed fields: Parent (links to the parent document name), Parenttype (the parent DocType), and Parentfield (the field name on the parent). You never set these manually. Frappe manages them.

You link a Child Table to a parent DocType via a Table field. From code, doc.items gives you the list of child rows. Each row is a document object with its own fields.

Naming Series

Every submittable DocType needs a Naming Series configured in the DocType settings. This generates sequential document names like BOOK-2026-00001 automatically. Set it before you create any test records, or your early test records will have ugly auto-generated names.

Fetching Values from a Linked Document

When a user selects a Coach from the Link field, you want to automatically pull that coach's hourly_rate into the Court Booking form. There are two ways to do this.

// Method 1: add_fetch — simple, declarative
// frm.add_fetch(link_fieldname, source_fieldname, target_fieldname)
frm.add_fetch("coach", "hourly_rate", "hourly_rate");
// When coach changes, Frappe fetches hourly_rate from Coach Profile
// and puts it in the hourly_rate field on Court Booking.

// Method 2: frappe.db.get_value — explicit, gives you more control
coach: function(frm) {
    if (frm.doc.coach) {
        frappe.db.get_value("Coach Profile", frm.doc.coach, "hourly_rate")
            .then(function(r) {
                frm.set_value("hourly_rate", r.message.hourly_rate);
                calculate_price(frm);
            });
    }
}
Computing a Derived Field in Real Time
function calculate_price(frm) {
    if (frm.doc.start_time && frm.doc.end_time && frm.doc.hourly_rate) {
        // Convert time strings to minutes since midnight
        var start = frm.doc.start_time.split(":");
        var end   = frm.doc.end_time.split(":");
        var start_mins = parseInt(start[0]) * 60 + parseInt(start[1]);
        var end_mins   = parseInt(end[0])   * 60 + parseInt(end[1]);
        var hours = (end_mins - start_mins) / 60;

        frm.set_value("duration_hours", hours);
        frm.set_value("total_price", hours * frm.doc.hourly_rate);
    }
}

frappe.ui.form.on("Court Booking", {
    start_time: function(frm) { calculate_price(frm); },
    end_time:   function(frm) { calculate_price(frm); },
    hourly_rate:function(frm) { calculate_price(frm); }
});

Server Scripts

Add backend validation and automation. Server Scripts run on the server, in Python, with access to the database. They are more powerful than Client Scripts and execute even when the form is saved via API (not just the browser UI).

The doc Object in Server Scripts

In a Server Script of type DocType Event, the doc object is already available representing the current document. You do not need to call frappe.get_doc(). Write doc.customer_name directly.

Conflict Detection Pattern

This is the Conflict Prevention Engine for the capstone. The pattern queries for existing bookings that overlap with the current one and throws an error if any are found.

# Server Script: DocType Event — Court Booking — validate

# Step 1: Get all other bookings for the same court on the same date
existing = frappe.get_all("Court Booking",
    filters={
        "court": doc.court,
        "booking_date": doc.booking_date,
        "name": ["!=", doc.name],   # exclude the current document
        "docstatus": ["!=", 2]       # exclude cancelled bookings
    },
    fields=["name", "start_time", "end_time", "member_name"]
)

# Step 2: Check each result for time overlap
for booking in existing:
    # Overlap condition: new booking starts before existing ends
    # AND new booking ends after existing starts
    overlaps = (doc.start_time < booking.end_time and
                doc.end_time > booking.start_time)
    if overlaps:
        frappe.throw(
            "Court {0} is already booked from {1} to {2} (Booking: {3})".format(
                doc.court,
                booking.start_time,
                booking.end_time,
                booking.name
            )
        )

# Step 3: Repeat the same check for the coach (if assigned)
if doc.coach:
    coach_bookings = frappe.get_all("Court Booking",
        filters={
            "coach": doc.coach,
            "booking_date": doc.booking_date,
            "name": ["!=", doc.name],
            "docstatus": ["!=", 2]
        },
        fields=["name", "start_time", "end_time"]
    )
    for booking in coach_bookings:
        if doc.start_time < booking.end_time and doc.end_time > booking.start_time:
            frappe.throw(
                "Coach {0} is already booked during this time (Booking: {1})".format(
                    doc.coach, booking.name
                )
            )

DAY 07
The Anatomy of a Frappe App

Understand what bench new-app creates and why each folder and file exists.

Create and Install the App

cd ~/frappe-bench-v16

# Install the app on your local development site

# Confirm it is installed
bench --site your_site_name.local list-apps
The File Structure
kuwa_tennis/
    kuwa_tennis/
        modules.txt             # lists the app's modules (Scheduling, Retail, etc.)
        hooks.py                # THE most important file — wires events to Python functions
        __init__.py
        scheduling/             # module folder
            __init__.py
            module_def.json     # module definition

                court_booking/

        retail/                 # second module folder
            ...
What hooks.py Does

hooks.py is a Python file that Frappe reads at startup. It is a configuration file that tells the framework which Python functions to run on which events. Every automation in your app is registered here. If you add a new function and do not register it in hooks.py, Frappe does not know it exists.

Critical rule: after any change to hooks.py, restart the bench. Unlike Server Scripts in the browser which apply immediately, app code changes require a restart.

        """Runs when the booking is submitted."""
        self.send_confirmation_notification()

    def check_booking_conflicts(self):
        """Prevent double-booking of courts and coaches."""
        # conflict detection logic goes here
        pass

    def calculate_total_price(self):
        """Compute duration and price server-side as a backup to the Client Script."""
        pass

# After every meaningful working change, commit it

git commit -m "Add conflict detection to Court Booking validate"

# View your commit history
git log --oneline

# If something breaks and you need to go back to a working state
git stash                  # save current uncommitted changes aside
git checkout [commit hash] # move to a previous commit
# OR to just discard all uncommitted changes:
git checkout -- .          # restore all files to last commit

Automation Modules

Build these after all DocTypes are tested and working with no scripts attached. Each module is independent. Test each one in isolation before combining.

Module 01 Real-Time Pricing Engine
TypeClient Script on Court Booking
Triggeron_change events on start_time, end_time, and hourly_rate. Fetch trigger on coach field change.
LogicWhen coach changes, fetch hourly_rate from Coach Profile via frappe.db.get_value. When start_time, end_time, or hourly_rate changes, compute duration_hours as the time difference in decimal hours and total_price as duration_hours multiplied by hourly_rate. Set both fields via frm.set_value so they display in real time without a save.
GoalUser sees the price update live as they adjust the booking. No save required to see the cost.
Also addA server-side calculation in the validate method of CourtBooking as a backup, so price is always correct even on programmatic saves.
Module 02 Conflict Prevention Engine
TypeServer Script (validate event) on Court Booking. Move to Python controller in Phase 2 consolidation.
TriggerBefore every save of a Court Booking document.
LogicQuery existing Court Booking records for the same court on the same date, excluding the current document and cancelled records. For each result, check whether the time ranges overlap using the condition: new start is before existing end AND new end is after existing start. If any overlap exists, throw an error naming the conflicting booking and the time range. Repeat the check for the assigned coach if a coach is set.
GoalZero double-bookings on courts or coaches. The error message tells staff exactly which existing booking conflicts.
Edge casesCancelled bookings must be excluded. The current document must be excluded from its own conflict check (using name != doc.name). Test with a booking that exactly touches another (end time of one equals start time of another — this should NOT be a conflict).
Module 03 Inventory Depreciation Hook
TypeServer Script (on_submit event) on Retail POS. Move to Python controller in Phase 2 consolidation.
TriggerWhen a Retail POS document is submitted (status changes to Submitted).
LogicLoop through each line item in the items child table. For each item, fetch current stock_quantity from Pro Shop Item using frappe.db.get_value. Subtract the purchased quantity. If the result is below zero, throw an error identifying the item and its available stock. If the result is zero or positive, update stock_quantity using frappe.db.set_value. After updating, if the new stock_quantity is below the item's reorder_level, create a Frappe notification to alert the administrator.
GoalStock quantities stay accurate in real time. Staff cannot sell more than is in stock. Low stock alerts fire automatically.
Also handleon_cancel: when a Retail POS is cancelled, reverse the stock deduction by adding the quantities back to stock_quantity.
