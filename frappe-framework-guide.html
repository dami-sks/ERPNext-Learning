Module 01

Build

The architecture layer of Frappe. Define data structures, create custom views, build reports, and extend the system without touching app source code. Master this module and everything else follows.

DocType Core Concept

DocType is the single most important concept in all of Frappe. Every entity you work with — a Sales Invoice, a Customer, a Purchase Order, a custom data table you create — is a DocType. When you define a DocType, Frappe automatically creates the database table, generates the form UI from your field definitions, and wires up all CRUD operations. No manual SQL or form coding required.

Frappe transforms DocType names into database table names by prefixing with tab. A DocType named Work Order becomes the table tabWork Order. You will see this prefix in raw SQL and the System Console.

Auto Naming

  • Naming Series (e.g., SINV-.YYYY.-.####): generates sequential IDs like SINV-2025-0001. Use .YYYY., .MM., or .DD. for date segments. #### is the auto-incrementing zero-padded counter.
  • field:fieldname: uses the value of a specific field as the name. Common for master data where the name is meaningful (e.g., Customer).
  • Prompt: user types the name when creating the record.
  • Auto: Frappe generates a random hash. Use only when the name does not need to be human-readable.
  • format:{field1}-{field2}: combines field values into the name at save time.

💡
Always add at least one permission row

If a DocType has zero permission rows, only System Manager can access it. Always add permissions even for internal DocTypes, or users will get blank screens with no explanation.

The Permissions Tab

Each row in the Permissions tab specifies a Role and what it can do on this DocType. Permission types available: Read, Write, Create, Delete, Submit, Cancel, Amend, Report, Export, Import, Share, Print, Email. Set the Level to match field-level permissions where needed.

Creating a DocType: Step by Step

  1. Go to Build > DocType > New (or press Cmd/Ctrl+K and search "New DocType").
  2. Enter a DocType Name in Title Case (e.g., "Field Service Report" not "fieldservicereport").
  3. Set the Module to control sidebar placement.
  4. Set flags: Is Submittable for transactional documents, Is Child Table for line-item tables.
  5. Set Auto Name: naming series for transactional docs (e.g., FSR-.YYYY.-.####), or field:fieldname for masters.
  6. Click Add Row in the Fields table. Add fields one by one, using Section Break and Column Break to organize the layout.
  7. Switch to the Permissions tab and add at least one Role with appropriate permissions.
  8. Save. Frappe creates the database table immediately.
⚠️
Renaming fieldnames after data exists is dangerous

Renaming a fieldname after data has been saved creates an empty new column and leaves data in the old (now orphaned) column. Plan your fieldnames carefully before going live. Deleting a field only hides it from the form — the database column remains.

ℹ️
DocTypes in desk vs DocTypes in app files

DocTypes you create through the desk (Build > DocType > New) are stored in the database and apply to the site immediately. DocTypes defined in a custom app's source files are applied to a site by running bench --site yoursite.local migrate after installing or updating the app. If you modify a file-based DocType and your changes are not showing up, run bench migrate from the terminal.

Page

A Page is a standalone single-screen view in the Frappe desk that has no corresponding database table. Pages are for custom dashboards, utility tools, control panels, or any interface that does not follow the standard list-form data pattern.

Page vs DocType

  • Use a DocType when you need to create, store, and manage records (CRUD operations).
  • Use a Page when you need a custom interface without its own data model — aggregated views, calculators, configurators, or admin tools.

JavaScript — Page Script Example
frappe.pages['my-custom-page'].on_page_load = function(wrapper) {
    var page = frappe.ui.make_app_page({
        parent: wrapper,
        title: 'My Custom Page',
        single_column: true
    });

    // Add toolbar button
    page.add_action_item('Run Report', function() {
        frappe.call({
            method: 'frappe.client.get_list',
            args: {
                doctype: 'Sales Order',
                filters: [['status', '=', 'Draft']],
                fields: ['name', 'customer', 'grand_total'],
                limit: 20
            },
            callback: function(r) {
                // Render r.message into the page
                var html = r.message.map(function(row) {
                    return '<p>' + row.name + ' — ' + row.customer + '</p>';
                }).join('');
                $(wrapper).find('.page-content').html(html);
            }
        });
    });
};

Report

Reports extract, aggregate, and display data. There are four report types in Frappe, each suited for different needs. Choosing the right type is the first decision when building a report.

1. Query Report

You write raw SQL. Frappe executes it and displays the results. Best for complex joins and aggregations where you know exactly what SQL you need. Columns are defined inline in the query using a special format string.

SQL — Query Report
-- Column format: "Label:Fieldtype/Options:Width"
-- Put this SQL in the Query field of a Query Report DocType

SELECT
    so.name              AS "Sales Order:Link/Sales Order:150",
    so.customer          AS "Customer:Link/Customer:180",
    so.transaction_date  AS "Date:Date:100",
    so.grand_total       AS "Total:Currency:120",
    so.status            AS "Status:Data:100"
FROM `tabSales Order` so
WHERE
    so.docstatus = 1
    AND so.transaction_date BETWEEN %(from_date)s AND %(to_date)s
ORDER BY so.transaction_date DESC

2. Script Report

A Python function runs on the server and returns columns and data. Most flexible — you can call APIs, run multiple queries, transform data, and implement complex business logic.

Python — Script Report
def execute(filters=None):
    columns = [
        {"label": "Customer", "fieldname": "customer",
         "fieldtype": "Link", "options": "Customer", "width": 180},
        {"label": "Total Orders", "fieldname": "total_orders",
         "fieldtype": "Int", "width": 120},
        {"label": "Revenue", "fieldname": "revenue",
         "fieldtype": "Currency", "width": 140},
    ]

    conditions, values = "", {}
    if filters.get("from_date"):
        conditions += " AND so.transaction_date >= %(from_date)s"
        values["from_date"] = filters.from_date

    data = frappe.db.sql("""
        SELECT so.customer,
               COUNT(so.name)       AS total_orders,
               SUM(so.grand_total)  AS revenue
        FROM `tabSales Order` so
        WHERE so.docstatus = 1 {cond}
        GROUP BY so.customer
        ORDER BY revenue DESC
    """.format(cond=conditions), values, as_dict=True)

    return columns, data

3. Report Builder (Custom Report)

No-code. Select a DocType, choose columns, set filters, add sorting. Saved as a named Custom Report and accessible under the Report Builder option in any list view. Perfect for giving business users the ability to create their own standard views without coding.

4. Standard Report

Pre-built reports shipped with ERPNext and other apps. Defined in code files — you cannot create these from the desk. You can customize them (add or remove columns) using the Customize Report option in the report toolbar.

Adding Filters to Script and Query Reports

Workspace

Workspaces are the module home pages in the Frappe desk. When a user clicks a module name in the sidebar, they land on a Workspace. You can create custom Workspaces to organize shortcuts, charts, and number cards for specific roles or departments.

Workspace Components

  • Shortcuts: Clickable tiles linking to DocTypes, Reports, or Pages. Optionally show a count badge for open/draft records.
  • Dashboard Charts: Embedded charts from Dashboard Chart definitions.
  • Number Cards: Single KPI values (e.g., "Open Purchase Orders: 12") pulled from report data.
  • Custom Blocks: HTML or Markdown content blocks for announcements or documentation.

Creating a Workspace

  1. Go to Build > Workspace > New.
  2. Set the Name (used as URL slug), Label (displayed name), Module, and Icon.
  3. Optionally restrict to specific Roles for visibility control.
  4. Save. Navigate to the workspace to see the drag-and-drop editor via the Customize button.
  5. Add shortcuts, charts, and cards. Arrange by dragging.
  6. Click Save Customizations when done.
💡
Role-specific Workspaces per department

You can create multiple Workspaces for the same module, each restricted to a different role. A "Warehouse Supervisor" workspace and a "Procurement Manager" workspace under Stock can show completely different shortcuts and charts to the same people depending on which role they are assigned.

ℹ️
Workspace shortcut count badges

Workspace shortcuts can show a count badge next to the icon — for example "Purchase Invoices" with a badge showing 12 (for 12 open invoices). Enable this by checking Count on the shortcut configuration and setting the Doctype and optional filter. The badge auto-refreshes when the Workspace loads. This is the fastest way to turn a Workspace into a lightweight dashboard for a role.

Dashboard

A Dashboard is a dedicated page that groups charts and number cards into a single operational view. Dashboards can be embedded in Workspaces or opened as standalone pages from the desk. They are the primary tool for live visibility into KPIs, trends, and distributions without running a full report each time.

⚠️
Build the parts first, then assemble

The most important thing to understand about ERPNext dashboards: Dashboard Charts and Number Cards are their own separate DocType records. You create them independently, then link them into a Dashboard container. You do not build charts inline inside the Dashboard form itself. If you go to Build > Dashboard > New and click Add Chart, it prompts you to select an already-existing Dashboard Chart record. Nothing gets built there. The building happens earlier, in Build > Dashboard Chart and Build > Number Card.

The Assembly Sequence

  1. Build your Number Cards first: go to Build > Number Card > New. Create one card per KPI you want at the top of the dashboard.
  2. Build your Dashboard Charts: go to Build > Dashboard Chart > New. Create one chart per visualization.
  3. Create the Dashboard container: go to Build > Dashboard > New. Add your pre-built charts and cards by selecting them in the Charts and Cards child tables.
  4. Embed in a Workspace: navigate to the target Workspace, click Customize, drag in a Charts block, and select which Dashboard Chart or Number Card to embed.

Number Cards vs Charts: The Core Mental Model

Before building anything, apply this rule: one number at a time = Number Card; multiple numbers compared at once = Chart.

  • How many purchase invoices are outstanding right now? One number. Number Card.
  • How has revenue trended over the last six months? Many numbers across time. Chart.
  • What is the current stock level of one item? One number. Number Card.
  • Which suppliers account for what proportion of my spend? Multiple values in comparison. Chart.

Number Cards sit at the top of a Dashboard as the at-a-glance summary row. Charts fill the body below. A well-structured dashboard typically has 3 to 6 Number Cards at the top and 4 to 8 Charts in the grid below them.

Dashboard Chart: Two Separate Concepts

The Dashboard Chart form has two fields that look like the same thing but control entirely different decisions:

A Bar chart (Type = Bar) can use Count aggregation (Chart Type = Count). A Line chart (Type = Line) can use Sum aggregation (Chart Type = Sum). They are completely independent choices: one governs how the data is computed, the other governs how it is drawn on screen.

Three-Layer Filter Framework

Apply filters in this sequence for every chart and number card you build:

  1. Layer 1: Status. Always start here. Without a status filter, your chart or card includes Draft records that have not been posted yet, which inflates every number and makes the dashboard misleading. For transactional DocTypes (Sales Invoice, Purchase Invoice, Payment Entry, Delivery Note, Purchase Receipt, Quality Inspection), set Document Status = Submitted. For master data DocTypes like Bin, there is no docstatus field and this layer does not apply.
  2. Layer 2: Time. Scope to a relevant period. Use the Timespan field for a rolling window (Last Month, Last Quarter) or add a filter on Posting Date or Transaction Date for a fixed range. Without a time scope, your card or chart accumulates every record ever created, which quickly loses operational meaning.
  3. Layer 3: Scope. Narrow to the right slice of the business for the role viewing the dashboard. Common scope filters: Company (for multi-entity sites), Supplier Group or Customer Group, Item Group, Warehouse, Cost Center, Department. Only add scope filters that actually matter for the dashboard's intended user. A CEO dashboard needs the full picture; a warehouse supervisor dashboard needs their warehouse only.
⚠️
Document Status shows labels, not numbers in the filter builder

In the visual filter builder, the Document Status filter shows Draft, Submitted, and Cancelled as the dropdown options, not the numeric values 0, 1, and 2. Select the label. The underlying system stores and queries using the integer values internally, but the filter builder abstracts that away. If you type 1 into the filter value expecting Submitted, it will not work.

Stock KPIs: Use Bin, Not Stock Ledger Entry

When building a Number Card or chart for current stock levels, the common mistake is to use Stock Ledger Entry because that DocType appears in all the stock reports. This is wrong. Stock Ledger Entry is a transaction log, not a balance sheet.

DocTypeWhat it actually isUse for current-stock dashboards?
BinA live record per item per warehouse that holds the current stock balance. One Bin record = one item in one warehouse right now. Key fields: actual_qty (what is physically there), reserved_qty (committed to open orders), ordered_qty (on open purchase orders), projected_qty (actual minus reserved plus ordered).Yes. Always use Bin for current-state stock KPIs.
Stock Ledger EntryAn immutable row is created for every single stock movement ever made. It is a chronological history of what happened to stock, not a record of what exists now. Summing Stock Ledger Entry gives you the running total of all incoming and outgoing movements since the company was created, which is not the current balance.No. Summing SLE does not give you current stock.

Example: Number Card for current stock of one item: Document Type = Bin, Function = Sum, Aggregate Based On = actual_qty, Filter = Item Code = [item name].

Timespan Field Limitation

The Timespan field on Dashboard Charts offers only rolling backward windows: Last Day, Last Week, Last Month, Last Quarter, Last Year. There are no "Current Month", "This Week", "Month to Date", or "Year to Date" options in the native dashboard builder. The field looks backward from today by the selected period, not forward from a calendar boundary.

If you need a current-period window (for example, data from the first of this month through today), you have two paths:

  • Build a Script Report that handles the date logic on the server, then create a Dashboard Chart with Chart Type = Report pointing to that report.
  • Use Frappe Insights, which offers full date range flexibility including period-to-date calculations.
ℹ️
When to escalate to Frappe Insights

Native ERPNext dashboards work well for straightforward counts, sums, and groupings from a single DocType. Reach for Frappe Insights (a separate installable app: bench get-app insights) when your KPI requires: division (e.g., gross margin percentage requires revenue minus cost divided by revenue, which native charts cannot compute); multi-table joins (e.g., comparing a parent document value against a child table value in the same calculation); child table parameter extraction (e.g., pulling the reading for a specific quality parameter from a Quality Inspection Readings child table row); or comparison against a known standard or threshold (e.g., actual yield rate versus the budgeted yield in a separate master record). If you find yourself trying to work around a calculation using two separate charts and asking the viewer to do the math mentally, that is the signal to install and use Frappe Insights instead.

Auto-Refresh

Dashboard charts can be configured to auto-refresh at a set interval. On the Dashboard page, click the refresh interval selector in the top-right corner. Options range from every 1 minute to every hour. Use this for operational dashboards that are displayed on a screen in a warehouse, production floor, or operations room.

ℹ️
Performance note on frequent auto-refresh

Each chart refresh fires a database query. On a busy production server with many users watching dashboards on 1-minute refresh cycles, this creates noticeable load. Enable the Use Cache option on individual charts to reduce database hits. The cache is refreshed by the Frappe scheduler so 50 users watching the same chart only cause one database query per cache interval rather than 50.

Workflow Customization

Workflows add state-machine behavior to DocTypes. Instead of a single Save/Submit button, documents move through defined States via Actions, and each transition can be restricted to a specific Role. This is how you implement approval flows, review chains, and multi-stage document pipelines.

Core Concepts

  • States: The stages a document can be in (Draft, Pending Approval, Approved, Rejected, etc.).
  • Transitions: Rules defining who can move a document from one State to another via which Action.
  • Actions: The button labels that appear on the form (Submit for Approval, Approve, Reject, etc.).
  • Document Status: Each State maps to a Frappe docstatus: 0 = Draft, 1 = Submitted, 2 = Cancelled.

Setting Up a Workflow

  1. Go to Build > Customization > Workflow > New.
  2. Set the Document Type you want to add workflow behavior to.
  3. Set the Workflow State Field — the field that will store the current state. Frappe prompts you to create it if it does not exist.
  4. In the States table: add state names, map each to a Document Status (0/1/2), and optionally set a style color.
  5. In the Transitions table: for each transition set From State, To State, Action (button label), and Allowed Role.
  6. Optionally check Send Email Alert on transitions to trigger notifications automatically.
  7. Save. Navigate to the DocType form — workflow action buttons replace the standard Save/Submit toolbar.
⚠️
One Workflow Per DocType

Only one active workflow can exist per DocType at a time. Changing state names after records already exist in those states can break those existing records. Plan your states carefully before deploying to production data.

Server Script Customization

Server Scripts run Python code on the Frappe server without editing any app files. This is one of the most powerful tools in Frappe: you can automate field calculations, enforce business rules, expose API endpoints, and schedule background tasks — all from the desk UI with no deployment required.

DocType Event Triggers

  • Before Insert: Before a new document is saved for the first time. Good for setting computed defaults.
  • After Insert: After a new document is committed to DB. Good for creating related records.
  • Before Validate: Before the system runs its own validation. Runs on every save attempt.
  • Validate: After Before Validate. Your main place to throw validation errors.
  • Before Save: Last chance to modify before write to DB.
  • After Save: After a successful save. Good for syncing data to other DocTypes.
  • Before Submit / After Submit: Around submission (docstatus 0 to 1).
  • Before Cancel / After Cancel: Around cancellation (docstatus 1 to 2).
  • Before Delete / After Delete: Around document deletion.
Python — Server Script Reference
# In DocType Event scripts, the document is available as 'doc'
# Full Frappe Python API is available

# --- Read and set field values ---
doc.status = "Pending Approval"
doc.approved_by = frappe.session.user
current_total = doc.grand_total

# --- Throw a validation error (stops save) ---
if doc.grand_total < 0:
    frappe.throw("Grand total cannot be negative.")

# --- Non-blocking message to user ---
frappe.msgprint("Document saved. Awaiting approval.")

# --- Fetch another document ---

doc.credit_limit = customer.credit_limit

# --- Database: get a single field from a single record ---
customer_group = frappe.db.get_value("Customer", doc.customer, "customer_group")

# --- Database: get a list of records ---
open_orders = frappe.db.get_all(
    "Sales Order",
    filters={"customer": doc.customer, "status": "Draft"},
    fields=["name", "grand_total"],
    order_by="creation desc",
    limit=10
)
for o in open_orders:
    print(o.name, o.grand_total)

# --- Database: raw SQL ---
result = frappe.db.sql("""
    SELECT SUM(grand_total) AS total
    FROM `tabSales Order`
    WHERE customer = %(customer)s AND docstatus = 1
""", {"customer": doc.customer}, as_dict=True)
total = result[0].total if result else 0

# --- Create a new document ---
task = frappe.get_doc({
    "doctype": "Task",
    "subject": "Review order {}".format(doc.name),
    "assigned_to": doc.owner,
    "status": "Open"
})
task.insert(ignore_permissions=True)

frappe.db.set_value("Sales Order", doc.name, "custom_flag", 1)
frappe.db.commit()  # Always commit explicit DB writes

# --- Permission Query Conditions (returns SQL string) ---
# 'user' variable is available automatically
conditions = "`tabSales Order`.owner = '{}'".format(user)

Client Script Customization

Client Scripts run JavaScript in the user's browser on Frappe forms. They control UI behavior: showing or hiding fields based on conditions, calculating values when a field changes, adding custom buttons, validating input, and fetching server data without a full page reload.

JavaScript — Client Script (complete structure)
frappe.ui.form.on('Sales Order', {

    // Runs once when the form first loads
    onload: function(frm) {
        // One-time setup: configure field options, set filters, etc.
        frm.set_query('warehouse', function() {
            return { filters: { company: frm.doc.company } };
        });
    },

    // Runs on every render (load, save, submit, refresh)
    // This is your main event handler
    refresh: function(frm) {
        // Clear buttons first to avoid duplicates
        frm.clear_custom_buttons();

        // Add a button only on submitted documents
        if (frm.doc.docstatus === 1) {
            frm.add_custom_button('Create Delivery', function() {
                frappe.confirm('Create a Delivery Note?', function() {
                    frappe.call({
                        method: 'erpnext.selling.doctype.sales_order.sales_order.make_delivery_note',
                        args: { source_name: frm.doc.name },
                        callback: function(r) {
                            var doc = frappe.model.sync(r.message);
                            frappe.set_route('Form', 'Delivery Note', doc[0].name);
                        }
                    });
                });
            }, 'Create');  // Groups under a "Create" dropdown
        }

        // Show/hide a field dynamically
        frm.toggle_display('custom_approval_note',
            frm.doc.status === 'Pending Approval');
    },

    // Triggers when the 'customer' field changes
    customer: function(frm) {
        if (!frm.doc.customer) return;
        frappe.db.get_value('Customer', frm.doc.customer,
            ['payment_terms_template', 'credit_limit'],
            function(r) {
                frm.set_value('payment_terms_template', r.payment_terms_template);
                // Show the fetched credit limit in a message
                if (r.credit_limit) {
                    frappe.show_alert('Credit limit: ' + format_currency(r.credit_limit));
                }
            }
        );
    },

    // Triggers when 'qty' changes in the items child table
    // cdt = child DocType name, cdn = child row name (ID)
    'items.qty': function(frm, cdt, cdn) {
        var row = frappe.get_doc(cdt, cdn);
        frappe.model.set_value(cdt, cdn, 'amount', row.qty * row.rate);
        frm.refresh_field('items');
    },

    // Validate before save — frappe.throw() blocks save
    validate: function(frm) {
        if (frm.doc.grand_total <= 0) {
            frappe.throw('Order total must be greater than zero.');
        }
        if (!frm.doc.delivery_date) {
            frappe.throw('Delivery date is required.');
        }
    },

    // Runs before the user submits the document
    before_submit: function(frm) {
        if (!frm.doc.customer_po_number) {
            frappe.msgprint('Warning: No customer PO number entered.');
            // Does not block submit — use frappe.throw() to block
        }
    }
});

Customize Form Customization

Customize Form is the safest way to modify existing DocTypes — including all standard ERPNext DocTypes like Sales Invoice, Customer, Purchase Order — without touching source code and without breaking on app upgrades.

What You Can Do

  • Add new fields to existing DocTypes
  • Reorder existing fields by dragging rows

  • Remove core fields entirely — only hide them
💡
Clear cache if customizations are not taking effect

Frappe caches DocType metadata aggressively. If you save a customization and do not see the change on the form, run System > Tools > Clear Cache from the desk, or execute bench --site yoursite.local clear-cache from the CLI. Cached metadata can mask newly saved customizations, especially on multi-user production sites.

  1. Go to Build > Customization > Customize Form.
  2. In Select DocType, type the name of the DocType you want to modify.
  3. The field list appears. Drag rows to reorder. Click any row to edit its properties. Click Add Row to add a new custom field.
  4. Set Insert After on new fields to control placement precisely.
  5. Click Update to apply. Use Reset to Defaults to undo all customizations for this DocType.
💡
Use Customize Form over Custom Field when making multiple changes

Customize Form shows all fields in context, making it much easier to place new fields correctly and understand the overall form structure. Custom Field is faster only when adding a single field in isolation.

Module 02

Automation

Tools for automating recurring tasks, routing documents to the right person, tracking lifecycle milestones, and scheduling reports. Let Frappe handle the repetitive work.

Assignment Rule

Assignment Rules automatically assign documents to users when they are created or updated. They replace the manual process of a supervisor routing each incoming task, ticket, or order to a team member.

Assignment Methods

  • Round Robin: Cycles through a list of users in sequence. User 1 gets document 1, User 2 gets document 2, and so on, then repeats. Fair and predictable.
  • Load Balancing: Assigns to the user in the list who currently has the fewest open assignments. More intelligent than round robin when workload varies.
  • Based on Field: Assigns to whoever is named in a specific field on the document (e.g., the "Assigned Sales Person" field). Use when the document already carries the assignee information.

Module 03

Data

Import records in bulk, export filtered data, run mass updates, manage backups, and recover deleted documents. The Data module is your data operations center.

Data Import

Data Import lets you create or update many records at once using a CSV or Excel file. Essential during initial implementation (importing master data like customers, items, suppliers) and for ongoing bulk operations.

Import Process

  1. Go to Data > Data Import > New.
  2. Select the Document Type you want to import into.
  3. Select Import Type: "Insert New Records" or "Update Existing Records".
  4. Click Download Template. This generates a CSV with the correct column headers for the DocType.
  5. Fill in the template with your data. Do not change the column headers.
  6. Upload the completed file using the Attach button.
  7. Click Import. A background job starts. Progress displays on screen.

Template Structure Rules

  • The first row is column headers (fieldnames) — never modify these.
  • For Link fields: enter the exact name or ID of the linked document. Case-sensitive.
  • For Date fields: use the format from System Settings (usually YYYY-MM-DD).
  • For Select fields: value must exactly match one of the defined options. Case-sensitive.
  • For child tables (e.g., Invoice Items): each child row is a separate CSV row, with the parent ID repeated in the first column.
  • For Update mode: the name column (document ID) is required so Frappe knows which record to update.

Error Handling

When some rows fail and others succeed, Frappe logs each failure with a reason. You can click Download Errored Rows to get a CSV of only the failed rows (with the error reason in an extra column). Fix the issues and re-import that file. Successfully imported rows are committed even when others fail.

⚠️
Validate before full import

For large imports (thousands of rows), click Validate Data first. This runs all import logic without actually saving anything, letting you catch errors before committing the full dataset.

Data Export

Data Export downloads filtered records from any DocType as a CSV or Excel file. Useful for reporting, data analysis in external tools, and preparing data for re-import after bulk modification.

  1. Go to Data > Data Export.
  2. Select the Document Type.
  3. Set Filters to narrow down which records to export.
  4. In Select Fields, choose which fields to include.
  5. Select the file format: CSV or Excel.
  6. Click Export.
💡
Export, modify, re-import pattern

A powerful workflow: export a set of records, modify the file in Excel (e.g., change a field value across many rows), then re-import using "Update Existing Records" mode. This is often faster and safer than Bulk Update for complex multi-field changes because it goes through normal document validation and events.

Bulk Update

Bulk Update applies a single field change to all records matching your filters in one operation. The fastest way to normalize data across many documents.

FieldPurpose
DocTypeWhich DocType records to update.
FieldThe specific field to change.
ValueThe new value to set.

The Backups screen provides access to site database backups. Take manual backups, configure scheduled backups, and download backup files for external storage.

Deleted Document

When a document is deleted through the Frappe UI (not via raw SQL), Frappe saves a full copy of its JSON data in the Deleted Document log. This provides both an audit trail and the ability to restore accidentally deleted records.

  1. Go to Data > Deleted Document.
  2. Search by DocType or by the document's original name.
  3. Open the Deleted Document record. It shows the full JSON of the deleted document.
  4. Click Restore. Frappe re-creates the document from the saved JSON.
  5. The restored document will be in Draft status regardless of its previous state.
ℹ️
Linked records are not auto-restored

Restoring a deleted document only restores that specific document. Child tables embedded in it are restored along with it, but any separately deleted linked documents or file attachments are not automatically recovered. Check related records after restoring.

A User is the login account. An Employee is the HR record. They are separate DocTypes linked via the "User ID" field on the Employee record. Role

Roles are named groups of permissions. You assign permissions to Roles, then assign Roles to Users. This makes permission management scalable: change a Role's permissions and every user with that Role is updated.

Built-in Roles

  • System Manager: Full access to everything. Assign only to system administrators.
  • Guest: Unauthenticated visitors. Permissions assigned to Guest apply to non-logged-in users accessing the portal.
  • All: All logged-in users. Permissions for "All" apply to every authenticated user.
  • Desk User: Required for any user who accesses the desk interface.

Creating a Custom Role

  1. Go to Users > Role > New.
  2. Enter a descriptive Role Name (e.g., "Warehouse Supervisor", "Finance Approver").
  3. Set Desk Access to Yes for internal users, No for portal-only roles.
  4. Save. Then configure DocType permissions for this role via Permission Manager.
💡
Role Profile: assign many roles at once

A Role Profile is a named template that bundles a set of Roles together. Instead of assigning ten individual Roles to each new Finance Manager user, create a "Finance Manager" Role Profile containing all ten Roles and assign the profile to the user. When you later add or remove a Role from the profile, every user with that profile is updated automatically. Create Role Profiles at Users > Role Profile.

User Permission

User Permissions restrict which specific records a user can access — not just which DocTypes, but which individual documents within them. This is how you implement multi-branch, multi-company, or territory-based access control.

How It Works

Permission Manager

PDF Generation Notes

Frappe uses wkhtmltopdf (or WeasyPrint on newer versions) to convert print formats to PDF. These engines differ slightly from browser rendering:

Background Jobs

Frappe uses Redis Queue (RQ) to run tasks asynchronously in the background. This covers everything from scheduled automation (Auto Repeat, Email Reports, Reminders) to long-running operations (Data Import, PDF generation) to framework internals.

RQ Job

The RQ Job list shows all current, queued, completed, and failed jobs. Key fields: Status (queued, started, finished, failed), Queue (default, long, short), Job Name (the Python function), and Exc Info (the traceback on failure). You can manually retry failed jobs from the list view.

RQ Worker

Workers are the processes that pull jobs from Redis queues and execute them. In a healthy installation, you should see at least one worker per queue type (default, long, short). If no workers are running, all background jobs pile up in the queue without executing. Worker management is done via the bench CLI on the server, not from the desk.

Tools

System Console

The System Console is a live Python REPL running on your Frappe server. You can execute any Python code with full access to the frappe API, your database, and all installed apps. It is the most direct way to do one-off data fixes, test a script before putting it into a Server Script, or investigate system state in real time.

Python — System Console Examples
# Inspect a document
doc = frappe.get_doc("Sales Invoice", "SINV-2025-00123")
print(doc.status, doc.grand_total, doc.outstanding_amount)

# List documents matching conditions
orders = frappe.db.get_all("Sales Order",
    filters={"status": "Draft", "transaction_date": ["<", "2025-01-01"]},
    fields=["name", "customer", "grand_total"])
for o in orders:
    print(o.name, o.customer)

# Safely update a field (always commit)
frappe.db.set_value("Customer", "CUST-00001", "custom_segment", "Enterprise")
frappe.db.commit()

# Raw SQL with safety
result = frappe.db.sql("""
    SELECT COUNT(*) AS cnt, SUM(grand_total) AS total
    FROM `tabSales Order`
    WHERE docstatus = 1
    AND YEAR(transaction_date) = 2025
""", as_dict=True)
print(result[0])

# Reload all cached DocTypes after manual changes
frappe.clear_cache()

# Check installed apps
print(frappe.get_installed_apps())

# Get site config
print(frappe.conf.db_name, frappe.conf.site_name)
💡
bench execute: run Python functions from the terminal

For scripts you want to run from the CLI without opening the desk, use bench --site yoursite.local execute module.path.to.function. The function runs in the Frappe context with full database access, exactly like the System Console but from the terminal. Useful for one-off data migrations, testing scheduled functions manually, or running fixes on a server via SSH.

🚨
System Console has no undo

Code in the System Console runs immediately on your live database. Always test on a staging site first. Always include frappe.db.commit() explicitly for DB writes — never rely on auto-commit. For destructive operations, add a tight WHERE condition and use a Limit clause to test on a small subset before running on the full dataset.

Recorder

The Recorder captures all database queries executed during a specific request. Use it for performance profiling — identifying slow, redundant, or excessive queries that degrade page load or form submit speed.

  1. Go to System > Tools > Recorder.
  2. Click Start to begin recording.
  3. Perform the action you want to profile (open a form, submit a document, load a report).
  4. Return to Recorder and click Stop.
  5. Browse the recorded requests. Click any request to see the full SQL list with execution times, call counts, and Python call stacks per query.

Common findings: N+1 queries (a loop that fires one DB query per row instead of one batched query), repeated identical queries (same data fetched multiple times per request), and slow queries without proper database indexes.

Logs

Error Log

The most important log for developers. Every unhandled Python exception — from Server Scripts, scheduled jobs, form submissions, API calls — creates an Error Log entry with the full Python traceback, the request URL, and the timestamp. Check here first when a form fails to save, a scheduled job does not run, or an API returns a 500 error. The traceback tells you exactly which line of code failed and why.

API Request Log

Records every API call to the Frappe server: URL, HTTP method, response code, and execution time. Use this to audit which external systems are calling your Frappe API, identify slow endpoints by execution time, debug integration failures, and track usage patterns.

View Log

Records document view events: who opened which document and when. This is the data behind the "Seen By" list that appears in the document timeline, showing which users have opened the document.

Patch Log

Records every database migration patch applied to the site. Frappe apps ship Python patches that run once during upgrades to migrate schema or data. The Patch Log tells you which patches have run, when, and whether they succeeded. Critical for diagnosing upgrade issues where a migration may have failed partway through.

Website Theme lets you customize the visual appearance of the public website by overriding CSS variables and adding custom SCSS. Create multiple themes and switch between them to test different looks.

FieldPurpose
Theme NameIdentifier for this theme.
Google FontSelect a Google Font to load for the entire public website.
Apply Font to HeadingsUse the selected font for h1-h6 tags.
Color Overrides (table)Override specific CSS variables: primary color, background, link color, button color, etc.
Custom SCSSSCSS compiled server-side for deeper styling control beyond CSS variable overrides.

Activating a Theme

  1. Create or edit a Website Theme record.
  2. Click Set as Default to make it active.
  3. The theme compiles and applies to all public pages immediately on save.
ℹ️
Theme scope is public website only

Website Theme only affects the public website. The Frappe desk has its own appearance settings accessible from your user profile menu under Display Settings, where you can switch between light and dark mode independently.
